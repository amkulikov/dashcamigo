# SEO and URL structure

Operational runbook for search-engine optimization and the multi-locale URL layout.
`CLAUDE.md` keeps only the two rules that touch day-to-day code (extension-less URLs,
git-mtime `lastmod`); the procedures, rationale, and engine-specific quirks live here.

## URL structure and root redirect

All locales (including English) live under `/<lang>/` - there is no "default locale at /" shortcut. The structure:

- `/` - **redirect stub**, no content. `<link rel="canonical" href="/en/">` + `<meta http-equiv="refresh" content="0; url=/en/">` for no-JS bots (Google treats instant meta-refresh as a redirect). NO robots noindex on production: noindex next to a canonical-to-another-page is a conflicting-signals combo Google explicitly discourages (noindex blocks the page instead of consolidating it); the redirect + canonical pair already keeps the stub out of the index. Staging builds still noindex the stub like every other page. Inline bootstrap script picks the locale by priority `localStorage > navigator > en` and `location.replace("/<lang>/...")`. The stub still ships full OG/Twitter meta with English copy because Slack/Telegram/Twitter unfurl bots may hit it.
- `/en/`, `/ru/`, `/de/`, ... - regular locale homes with full content, `<link rel="canonical" href="/<lang>/">` self-referencing.
- `/en/cameras/<slug>/`, `/ru/cameras/<slug>/`, ... - per-locale vendor pages.
- `/cameras/<slug>/` (legacy) - server-side 301 to `/en/cameras/<slug>/` via `dist/_redirects` (generated by `vite-plugins/redirects.ts`). CF Pages applies these on the edge - NOT Functions, just a static config file.
- `hreflang` cluster on every prerendered page: every locale points at its own `/<lang>/` plus `x-default` → `/en/` (the English variant - uniform fallback across the whole graph; the content-less redirect stub `/` is a poor x-default target, so we point at the real English content instead). `/pt/` additionally claims the generic `pt` code next to `pt-BR` (`extraHreflangs` in `SEO_LOCALES`): without the alias a pt-PT visitor matches nothing and falls through x-default to English, while Brazilian Portuguese is the obviously closer fallback. zh deliberately stays `zh-Hans`-only (a generic `zh` would claim Traditional readers for a Simplified page). The in-HTML hreflang block and `sitemap.xml` carry the same graph; pinned by `seo-prerender-build.test.ts`.

Share-link contract: any URL with an explicit locale segment is **share-safe**. URL always wins over localStorage/navigator (URL-first detection in the bootstrap and in `detectInitialLang`). A Russian user sharing `/ru/cameras/70mai/` lands every receiver on Russian, regardless of their browser language. The lang-suggestion banner (`src/ui/lang-suggestion-banner.ts`) offers a one-click switch when the receiver's `navigator.language` doesn't match the URL locale - dismissable for the current page view (dismissal scope lives in `src/ui/lang-suggestion-banner.ts`).

The `/` redirect logic on the **client** is deliberate: a static `_redirects` line for `/` could only pick one locale unconditionally - which defeats the priority chain. The trade-off: GoogleBot without JS sees `<meta refresh>` to `/en/` and the canonical link - that's enough to consolidate ranking signals onto `/en/` and reach all other locales via the sitemap + hreflang graph.

Source of truth for the locale list, URL segments, hreflang codes and `og:locale` mappings is `src/i18n/seo-config.ts` `SEO_LOCALES`. Adding a locale: append an entry there + dictionary file + a `BANNER_COPY` entry in `src/i18n/banner-copy.ts` (the file's header carries the why; `banner-copy.test.ts` fails on drift from the dictionaries).

## Search-engine SEO

Target queries: "dashcam player / viewer", "&lt;vendor&gt; player", and localized variants. Top engines across locales: Google (most locales), Bing (long tail + AI surfaces: Copilot, ChatGPT browse, DuckDuckGo, Brave, Yahoo non-JP), Yandex (RU), Naver (KO), Baidu (ZH, with constraints).

**What's wired in.** Static prerender covering locale homepages, the `/cameras/` vendor pages, the `/alternatives/` competitor pages, feature/guide pages, and `/privacy` - current page families and per-locale counts are generated by the vite-plugins listed under "Where to find specifics" below; don't restate the numbers here, they drift every time a page family grows. Every prerendered page gets self-referencing `canonical`, full `hreflang` graph, locale-tuned `og:*` / `twitter:*`, per-locale `<html lang>` + `<meta http-equiv="content-language">` (the only locale signal Baidu / Naver / older Bing read), and page-type-appropriate JSON-LD (the schema.org types and their per-page mapping live in `index.html`'s JSON-LD blocks and the page plugins listed below, not enumerated here). `sitemap.xml` carries `xhtml:link` alternates. URLs with independently trackable source files also get a real `<lastmod>` derived from `git log -1`; programmatic page families whose locale and slug content shares monolithic files omit it because a shared file mtime cannot identify which URL changed. CF Pages builds from a **depth-1 clone**, where `git log -1 -- <file>` does NOT fail - it answers HEAD for every tracked file, stamping every dated URL with the deploy's commit time. `git-mtime.ts` detects the shallow clone, runs `git fetch --unshallow` once per build, and omits `<lastmod>` entirely when the fetch fails. After changing anything in that area, verify that every emitted date belongs to an independently trackable URL source.

**Extension-less URLs.** CF Pages automatically 308-redirects `*.html` requests to the extension-less form (`/privacy.html` → `/privacy`). That means every canonical URL we control - in sitemap `<loc>`, in `<link rel="canonical">`, and in internal links / footers - must be the extension-less form: a canonical or sitemap entry pointing at the `.html` form is a 308-redirecting URL, which GSC treats as "Discovered - currently not indexed" instead of following to the 200. The physical file may stay as `public/privacy.html` (it's the source of truth for the lang-switcher SPA inside); only the URLs we expose to crawlers and users need to drop the `.html`.

**Webmaster verification.** Google + Yandex via DNS TXT (records live in the registrar, no in-repo trace). Bing supports the same DNS TXT / CNAME approach. Naver verification is intentionally skipped (Naver supports only a meta tag / HTML file, no DNS TXT). Baidu intentionally skipped: mainland China is unreachable from Cloudflare Pages without an ICP license, and Baidu downranks non-ICP sites; realistic `/zh/` audience is Taiwan / Hong Kong / Singapore / diaspora, where Bing and Google dominate.

### IndexNow

How the protocol works: we generate an arbitrary 8-128 char key ourselves (no console-issued token from any engine - IndexNow is unregistered push, not webmaster verification). Proof of ownership: a file at `https://dashcamigo.app/<KEY>.txt` whose body is the same key. When we POST a submission, we include `key` and `keyLocation`; IndexNow servers fetch the keyLocation, compare bodies, and either accept or reject. The key is NOT public: the spec says only you and the engines should know the key and its location. The file is served but never linked - it must stay out of the sitemap, robots.txt, the repo, and the SW precache allowlist (`vite-plugins/sw-precache.ts`), or anyone can spam IndexNow on the domain's behalf until engines throttle the key.

Where the key lives: the `INDEXNOW_KEY` GitHub Actions secret and nowhere else - the production build (the `deploy` job of `release.yml`) feeds it to `vite-plugins/indexnow-key.ts`, which emits `dist/<KEY>.txt`, and the ping reads the same secret. Deliberately in no file, not even `.env.example`: the repo carries zero trace of the value. The ping script pre-flight-checks the live keyLocation before submitting, so the baked file and the secret drifting apart (a half-deployed rotation) fails with one clear message instead of five opaque 403s.

Day-to-day usage: automatic. The `ping` job of `.github/workflows/release.yml` runs after the production deploy job of the same `v*` tag run (a push to `main` only deploys staging, which must never be pinged) and calls `scripts/indexnow-ping.mjs`, which fetches the **live** `https://dashcamigo.app/sitemap.xml` (what is deployed is what gets pinged) and POSTs every `<loc>` directly, in parallel, to each IndexNow engine in the `ENGINES` list of `scripts/indexnow-ping.mjs` (which also records why Amazon is skipped). The batch (grows with every new page family) is well under the per-request limit (10000) for every engine. Ad-hoc ping without a deploy: the manual run button of `.github/workflows/indexnow.yml` (workflow_dispatch), or locally `INDEXNOW_KEY=<key> npm run indexnow`.

**Why direct instead of `api.indexnow.org`.** We POST each engine directly rather than the global fan-out endpoint: it gives per-engine visibility (the script logs HTTP status per engine, so a Naver 422 or a Yep 5xx is obvious rather than silent), and the global endpoint's documented fan-out does not reliably reach Bing for this host, while a direct POST to the engine's own endpoint does. Exit code is 0 if at least one engine accepted; only a full sweep failure (everyone 4xx/5xx, or no network) exits 1.

Re-pinging unchanged URLs on every deploy is fine - individual engines may 429 once in a while; the script treats 429 as a per-engine soft pass (warns, keeps going, counts as accepted for exit-code purposes).

Rotating the key (if disclosed - e.g. it leaked into a commit or a log):
1. `openssl rand -hex 16` - generate a new value.
2. Replace the `INDEXNOW_KEY` GitHub Actions secret.
3. Redeploy production (a new tag). The chained ping uses the new key automatically; the old file 404s after the deploy, which is fine - only the current key needs to validate. The ping's pre-flight catches a half-done rotation (secret updated, prod not redeployed).

Engines other than the IndexNow five use their own channels: Google via Search Console + sitemap auto-discovery (no IndexNow); Baidu is intentionally unreached (see Baidu note above).

### Crawler fallbacks

**`<noscript>` fallback** in `index.html` body: page.title + meta.description (translated by prerender like other `data-i18n` elements) + brand links + continue link. Read by JS-disabled crawlers (Baiduspider, Yetibot/Naver, Yandex with JS rendering disabled in Webmaster) and by users with JS off.

**llms.txt** at `dist/llms.txt` for Anthropic / Perplexity / ChatGPT-search. Google's docs state it outright (ai-optimization guide): llms.txt is not needed for Google Search and does not affect visibility either way - it stays purely for the non-Google consumers. Built by `vite-plugins/llms-txt.ts`.

### Out of scope

Google `Indexing API` (closed to non-JobPosting / non-BroadcastEvent). Google `FAQPage` rich snippet (Google stopped serving it entirely and pulled the docs; schema stays because Bing reads schema.org for Copilot / AI answers, and Yandex / Naver still use it). Google `HowTo` rich result (dead - the feature pages keep the markup for the same Bing / AI-grounding reason, not for a Google widget). Yandex `Turbo Pages` (deprecated). Baidu `MIP` (deprecated). `WebSite + SearchAction` (no internal search). `meta name="author/publisher"` (ignored by all majors). `meta name="keywords"` (Google states it is not used in ranking, modern Yandex/Bing ignore it too - pure head noise). `X-Robots-Tag` on production (production indexing is controlled via `robots.txt` + `canonical`; staging builds DO emit `X-Robots-Tag: noindex` via `_headers` + per-page noindex meta, with robots.txt deliberately ALLOWING crawl so the noindex is visible to crawlers - see `SeoBuildOptions` in `vite-plugins/seo-prerender.ts`).
